# FlightOR 链路探讨

> 文档定位：记录开发过程中发现的链路设计问题、事实证据、候选方案与待验证结论。
> 本文是持续更新的设计讨论日志，不覆盖 `FLIGHTOR_ARCHITECTURE.md` 或已接受 ADR。
> 当讨论形成跨领域的正式决定时，应创建或修订 ADR，并在本文补充决定链接。

## 1、2026-09-08：研究搜索、LLM 合成与 CitedResearchProvider

**状态：讨论中**

### 问题背景

当前目的地研究把网页搜索和 LLM 合成拆成两个能力：

```text
Planner Agent
  ↓
research_destination
  ↓
ProductionResearchAgent
  ├─ ResearchSearchProvider：搜索网页来源
  ├─ ResearchSynthesisModel：根据来源整理研究发现
  └─ 服务端验证：检查结构、来源索引、地点、类别和证据状态
  ↓
Research Artifact
  ↓
确定性 Travel Guide Builder
```

当前生产搜索实现是 `SerpApiResearchSearchProvider`。它不调用 LLM，而是按服务端规则构造查询，调用 SerpApi 的 Google Organic Search，并对标题、摘要、URL、域名和发布时间进行清洗、限制与去重。

当前生产合成实现是 `OpenRouterResearchSynthesisModel`。它接收研究请求和带索引的来源摘要，调用 LLM 输出结构化 findings。服务端随后检查输出 Schema、来源索引和请求范围，不能让模型添加不存在的来源。



### 方案 A：SerpApi 搜索 + LLM 合成

优点：

- 搜索结果与模型合成分离，供应商可独立替换。
- 服务端能够看到并持久化模型接收过的来源集合。
- 搜索结果可以缓存、复用和重新合成。
- 容易分别测试搜索失败、模型失败和无有效来源等情况。

问题：

- 至少包含搜索和模型两类网络调用，链路较长。
- 多目的地、多问题可能产生多批搜索请求。
- 当前只使用 snippet，验证能力有限。
- 搜索结果搬运到 LLM 会增加 Token、延迟和实现复杂度。

### 方案 B：带联网搜索的 LLM

带联网搜索能力的 LLM 可以在一次上层调用中完成检索、筛选和初步整理，并返回带引用的结构化 findings。它应作为 `CitedResearchProvider` 的另一个实现，而不是拥有 Trip、Artifact 或 Goal 权限的第二个 Planner Agent。

优点：

- 可能减少显式的“搜索结果 → LLM”数据搬运。
- 模型可以根据搜索结果继续调整查询，提高语义相关性。
- 对开放式目的地研究可能获得更完整的上下文。

问题：

- 模型内部可能执行多次不可见搜索，不保证一定更快或更便宜。
- 不同供应商提供的引用粒度、页面正文、发布时间和搜索轨迹差异较大。
- 输出及引用具有非确定性，复现和缓存更困难。
- 容易与特定模型供应商强耦合。
- 如果 API 只返回 URL 而不返回可核对的证据片段，仍然不能视为完成事实验证。



## 2、逐日攻略骨架”发展为可以直接照着走的日内路线

如果产品要从“逐日攻略骨架”发展为可以直接照着走的日内路线，后续很可能需要通过 Provider 接入全球或区域性的外部数据服务。未必存在一个能够完整覆盖全球的单一 API，可以按能力分别接入并保留替换接口。

目前已实现：

- 根据 Trip Context 选择城市并分配停留天数；
- 按城市和日期搜索带来源的活动、景点及实用信息；
- 将合格的 Research findings 分配到对应城市的每一天；
- 保存 Route、Research 和 Travel Guide Artifact，并保留来源与版本关系。

目前尚未实现：

- 完整的全球 POI、景点和商家目录；
- 营业时间、临时闭馆、预约和门票信息；
- POI 坐标、距离、建议停留时长和适合时段；
- 公交、地铁、步行、驾车等周边交通路线与实时耗时；
- 按地理位置、开放时间、交通时间和用户节奏生成上午 / 下午 / 晚上的访问顺序；
- 数据缺失、冲突、过期时的日内路线降级策略。

当前 Travel Guide 更准确地属于“每天在哪个城市、有哪些带来源的可选活动”，还不是经过时空约束计算的可执行路线。目前只是将调查到的合法活动平均分配到留在这个城市的每一天，周边城市的活动会被排除在外

## 3、维护一个时刻更新的机场拓扑？

目前**没有维护“持续自动更新、全球完整”的机场拓扑**。后端已有可用的**版本化拓扑快照机制**，但当前是按需、局部同步。

具体情况：

- PostgreSQL 保存 `topology_versions`、`route_edges`、`schedule_services`、`connection_options`。路线查询读取最新的 `active` 快照：[postgres.ts (line 134)](D:\\FunnyProject\\flightor-repo\\backend\\src\\topology\\postgres.ts:134)。
- 每次 OAG 同步会复制旧快照、写入指定航线和日期范围的数据，再原子切换新版本：[sync.ts (line 222)](D:\\FunnyProject\\flightor-repo\\backend\\src\\topology\\sync.ts:222)。
- 但同步范围明确标记为 `partial`，且 `coverage_complete=false`：[sync.ts (line 101)](D:\\FunnyProject\\flightor-repo\\backend\\src\\topology\\sync.ts:101)。
- 同步需要调用受保护的管理接口，传入具体 `origin + destination + dateFrom/dateTo`，再由 Worker 执行：[admin-sync.ts (line 57)](D:\\FunnyProject\\flightor-repo\\backend\\src\\routes\\admin-sync.ts:57)。
- Worker 只是轮询已有任务队列；代码中没有发现定时遍历全球机场和航线、自动刷新拓扑的调度器：[worker.ts (line 37)](D:\\FunnyProject\\flightor-repo\\backend\\src\\worker.ts:37)。
- 普通机票搜索也不会触发拓扑刷新。文档明确要求试用阶段只执行显式、有界的同步任务：[oag-integration.md (line 72)](D:\\FunnyProject\\flightor-repo\\docs\\oag-integration.md:72)。
- 机场基础资料目前也是一次同步一个机场，并非全量机场目录定期同步：[oag-integration.md (line 56)](D:\\FunnyProject\\flightor-repo\\docs\\oag-integration.md:56)。

## 4、本地拓扑

```
机场 = Node
航线/航班服务 = Edge

PVG ─────→ NRT
 │
 ├────→ ICN ─────→ NRT
 │
 ├────→ KIX ─────→ NRT
 │
 └────→ HKG ─────→ NRT
```

但当前 FlightOR 没有把 Google Flights 返回的多段联程直接当作自己的路线事实，核心原因是 **FlightOR 想拥有自己的路线规划能力，而不是把路线规划完全外包给搜索 Provider。**

机场拓扑需要后端管理员手动更新

两种架构其实差别很大：

```
方案 1：Provider 决定路线

用户
 ↓
Agent
 ↓
Google Flights
 ↓
“这 10 条路线给你”
 ↓
FlightOR 排序/展示
```

FlightOR 本质上只是一个“航班搜索 UI + Agent”。

而当前设计更接近：

```
方案 2：FlightOR 自己决定路线

                 ┌→ Fare Provider：真实价格
用户 → Agent → Route Engine
                 ├→ Topology：有哪些连接可能
                 └→ 用户约束/Trip Context

                       ↓
                自己组合候选路线
                       ↓
                自己验证可行性
                       ↓
                自己做 Pareto 优化
```

把 Google Flights 返回的多段联程直接当作自己的路线事实，我认为也是可行的



## 5、research agent

**主要是多轮模型调用和工具查询的耗时叠加，而且前端要等整轮结束才显示回复。** 你的一条消息，实际触发了去程机票、回程机票和伦敦攻略研究。

按刚才的[真实请求日志](D:/FunnyProject/flightor-repo/backend/.demo/api-local-login-20260908-185830.stdout.log)，流程是：

| 累计时间   | 实际在做什么                                         |
| ---------- | ---------------------------------------------------- |
| 0–7 秒     | 主模型决定下一步，读取已有任务，解析深圳、伦敦       |
| 7–16 秒    | 再调用主模型，把日期、预算等写入行程                 |
| 16–33 秒   | 再调用主模型，建立攻略任务，查询去程机票             |
| 33–102 秒  | 再调用主模型，查询回程机票，研究伦敦景点、饮食和交通 |
| 102–150 秒 | 再调用主模型，发起补充研究，随后达到超时上限         |

**还没走到最终的逐日编排、校验和保存攻略，就已经耗尽了 150 秒。**

时间主要花在两个地方：

- **主模型调用了 5 轮，累计约 61 秒。** 每次工具返回后，都要重新请求模型，让它阅读结果、决定下一步。
- **两轮研究累计约 80 秒，第二轮未完成。** 一次“研究”内部还包含：多次 SerpApi 搜索 → 研究模型整理资料 → 来源校验 → 保存结果。第一轮实际安排了 3 次搜索，得到 13 条资料，并出现搜索失败警告。现有日志不能进一步拆出搜索和模型整理各占多少时间。

还有两个结构上的拖慢因素：

1. **机票查询和研究目前串行执行。** 它们都会保存结果，当前调度把这类工具统一当作有状态操作，采用比较保守的串行策略。
2. **没有实时进度或中途结果推送。** 后端已经查到机票时，前端仍只显示“正在理解你的需求”，所以感觉一直没有动静。

刚才修复的是**超时导致进程崩溃**。响应速度仍需要优化，重点应放在减少不必要的模型回合、并行独立查询，以及及时显示已得到的结果和进度。
