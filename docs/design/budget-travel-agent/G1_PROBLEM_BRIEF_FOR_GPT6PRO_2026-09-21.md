# FlightOR G1 阻塞问题说明与架构咨询

日期：2026-09-21。源码基线：`main@66daee6`；最近真实运行基线：`fe48d84`。本文供 GPT-6 Pro 独立咨询，可单独上传，不要求咨询方访问仓库。本文是问题分析及待评估选项，**不是已接受设计或新实现计划**。

## 1. 希望你帮助解决什么

我们正在开发旅行规划 Agent。真实测试中，攻略保存、领域完成状态和重新请求后的恢复已经成功，但输出仍出现不可靠的事实或预算承诺，因此 G1 整体验收未放行。

**核心矛盾：系统能够证明“攻略已保存且满足已编码的结构约束”，却不能证明“用户看到的全部事实和金额承诺都受证据约束”。** 当前证据校验是对已声明字段的校验，模型可以不声明字段，直接在研究摘要、攻略备注或最终回复中写事实。

请不要直接给出“换更强模型”“再加提示词”“再加一次反思”作为最终答案。希望你：

1. 判断下述根因分析是否成立，指出我们可能过度设计或误判的地方。
2. 给出最小、通用、可迁移的事实及预算合同，明确模型、研究服务、领域校验器、最终回复各自的职责。
3. 比较候选方案，给出推荐次序、失败模式和可停止的验收标准。
4. 在保留 Agent 自由规划能力的前提下，避免继续按失败样本补城市、票价或措辞特例。

请区分事实、推断与建议；若信息不足，指出最小补充证据。请提供接口/数据结构示例、兼容与迁移步骤、离线测试矩阵，以及何时才值得再做付费真实复验。

## 2. 产品目标与不变约束

用户给出目的地、日期、总预算和偏好，Agent 研究来源、选择景点、安排节奏、保存可恢复的攻略。支持“机票已自备”和“已采用航班后继续规划”两种入口。

- 保持一个自主 Planner，能够选择、跳过、调整工具次序并局部修复。研究服务是有边界的工具，不是另一个自主旅行规划者。
- 领域代码拥有 Goal/Run、已接受约束、持久化和完成判定；模型不能静默改预算口径、日期或已采用航班。
- 允许价格、开放时间、交通耗时保持未知。**目标不是证明未来所有事实，而是避免把未知写成确定事实，把参考信息写成保证。**
- 保留自然语言推荐理由、个性化选择和行程节奏；不希望把 Agent 退化成固定城市脚本。
- 当前路线是先优化现有 runtime，再完成测量和案例评估；尚未进入正式 M1/M2，也没有决定切换 DSH。

## 3. 系统与当前实现

前端是 Taro / React / MobX；后端是 Fastify / TypeScript，PostgreSQL 保存业务与 Artifact，Redis / worker 执行任务。

```text
用户输入 / 已采用航班
  → 认证 Agent API → CloudPlannerService → 单一 Planner / AgentRuntime
  → research_destination
      → SerpApi 搜索 → 部分官方正文读取 → Research 模型综合
      → ResearchArtifact（summary、sources、可选 claimEvidence）
  → Planner 编写攻略 → save_travel_guide
      → 领域校验 → 保存 TravelGuideArtifact → completion verifier
  → Planner 再生成最终自然语言 reply → 保存会话 / 返回用户
  → 新请求读取 workspace，恢复攻略
```

当前运行模型为 `deepseek/deepseek-v4-flash-0731`，经 OpenRouter；下游路由可能变化。GPT-6 Pro 本次仅作为咨询方，不是已经选定的生产模型。精简 Goal 路径开关 `PLANNER_LEAN_GOALS_ENABLED` 默认关闭，G1 独立验收进程中开启。

已实现的关键机制：

- Planner 上下文预加载、领域 Goal、稳定候选及局部修复、保存结果和阶段计时。
- `researchTypes` 表示探索范围，`requiredEvidenceTypes` 表示交付必须覆盖的类别，避免模型自选研究项变成用户未要求的硬义务。
- 活动日期证据与地点身份校验；save 和持久完成验证复用领域规则。
- `reference_only` 适用性和服务端提示：读到来源不等于已验证未来出行日仍适用。
- 正文 reader：最多 4 页、并发 2、每页超时 8 秒，限制大小和提取文本；官方来源优先，并有公共地址/DNS 等访问约束。
- 可选 `claimEvidence`：记录价格、开放时间、交通耗时的主体、值、原文、URL、读取时间和正文 hash。验证原文确实存在于该快照，状态仅为 `source_observed`。

上述约束有实际作用，但没有形成覆盖全部用户可见文本的事实合同。

需要承认验收治理问题：原始 G1 重点是两条真实保存/领域验收/恢复链路，评测协议同时要求日期、预算、来源等质量约束；逐轮发现问题后，日期证据、价格时效、逐项声明完整性才变成更显式的合同。**不能声称这是完全冻结的同一内容标准下反复出现同一故障。**

这也不意味着应该回溯降低标准、直接宣布通过。需要明确区分“确定错误”“未提供逐项出处”“已清楚披露未知”“文案缺陷”，冻结各层退出条件。当前 runner 的 `passed` 检查保存、停止原因和恢复，不是内容质量评分器，容易与整体 G1 状态混淆。

## 6. 最新失败的可复现输入与输出

固定输入原文：

> 我的机票已自备，不查航班。请为2026年10月20日至21日东京两日游研究具体去处并保存攻略。本次两天游玩总预算1500元人民币，喜欢文化与小吃，节奏轻松，每天一个有来源的主景点，并提供实用交通或饮食信息。优先官方资料；未核实的价格、开放时间和交通耗时要明确说明。

保存结果：第 1 天浅草寺/仲见世与浅草居酒屋；第 2 天筑地场外市场与滨离宫。城市、日期、文化与小吃结构满足案例要求；持久化预算为 `1500 CNY / trip_total`。

研究/攻略实用资料出现 Tokyo Metro 180–330 日元、Toei 180–430 日元等票价区间，未附 claimEvidence。最终回复原样包含：

> The travel guide was saved successfully (completion status: satisfied). Let me summarize the result for the user clearly, including the source references and proper caveats about unverified prices/hours.

以及：

> Let me provide the final reply in Chinese (user's language), without internal narration.

中文部分又说：

> 本攻略两天游玩总额预算按 **1500 元人民币** 设定（不含未核实的具体门票/小吃单价，推荐另设小额小吃备用）。

> 两天主要开销会是地铁交通与小吃，符合你 1500 元的总预算。

同一回复也披露价格、时间未核实，但仍然给出无依据的总预算结论。前一句还有把未核实开销排除在总预算外的歧义。数据库中的正确预算字段不能抵消最终答复里的语义错误。

英文段是实际返回的可见 `message.content` / reply，**没有证据证明它是隐藏推理泄漏或某个特定 Provider 的 reasoning 协议错误**。

已选航班固定案例则要求依据已采用北京至东京航班、2026-10-20 至 21、全程 4,000 元、文化小吃、抵达前无活动、不重新查票/更换航班、不需要演出展览、未知费用和时间保持未知。它在前一批通过相关结构边界，最新代码尚未复跑，不能用自备票失败概括两条链路都失败。

## 7. 为什么现有校验放过了这些输出

### 7.1 可选证据合同存在省略通道

以下是当前逻辑的等价简化，非完整源码：

```ts
const claims = admitClaimEvidence(draft.claimEvidence, sources, sourceIndexes)
const rejectedClaims = (draft.claimEvidence?.length ?? 0) > claims.length
// 不传 claimEvidence → 空数组 → 不触发 rejectedClaims
// summary 仍是模型自由生成的字符串
```

save 校验要求攻略条目的 description 等于研究 finding.summary，且 claimEvidence 与研究一致。这样能防止 Planner 擅自修改研究，但**忠实复制一个缺证据的摘要仍然可以通过**。空数组之间也满足一致性和“没有冲突”。

当前 claimEvidence 的实际证明能力是：URL 对应快照、hash/时间一致、quote 存在于正文、value 存在于 quote。它不证明主体理解正确、事实适用于本次行程、来源没有过时，也不发现所有未声明的事实。冲突检查只覆盖同一 finding 内、同种类/同名主体的不同值，不是跨来源语义冲突解析器。

### 7.2 预算守恒与预算可行性混为一谈

领域代码验证攻略预算金额、币种、口径等与 Trip 一致。这回答“有没有篡改约束”，没有回答“纳入了哪些成本、未知项有多少、合计是否有依据”。当前没有足以支持上述预算保证的成本账本。

需要决定：什么情况下只能说“目标预算为 1,500 元，尚不能判定是否满足”，什么情况下允许说“已核实部分为 X”，什么条件才允许给总预算判断。未知不能当作零，也不能从总预算范围排除。

### 7.3 最终回复重新开放了事实生成

Artifact 校验完成后，Planner 仍生成新的自由文本 reply，CloudPlannerService 保存并返回 `result.reply`。因此，即使进一步收紧 Artifact，最终回复仍可能新添票价、预算保证和元叙述。

需要处理的不是单个英文前缀，而是“保存后的最终表述是否也遵守同一事实合同”。提示词已有相关禁止要求，但真实输出没有可靠遵守。

### 7.4 取证能力和内容合同是两个问题

最新正文读取 4 页仅 2 页成功，另有 HTTP 403 和 HTTP 200 后正文未被 reader 接纳；后者日志不能确定具体原因。成功读取的是旅游页面，不等于每条价格都有当前运营方正文。

扩大读取覆盖可能改善材料，但不自动解决模型省略证据字段；强制所有事实均有正文，也可能让正常网页不可读时完全无法交付。应设计可降级为未知/参考的表达，而不是绕过访问限制或把搜索摘要包装成正文证据。

### 7.5 我们的实施与验证方法存在不足

之前的修复分别处理了日期、类别约束、适用性、正文出处，方向有价值；但没有先完整枚举所有用户可见事实出口，因而仍留下 summary、备注和最终 reply 的旁路。离线测试证明了已编码合同，没有证明合同覆盖完整。

完整后端离线测试曾通过 99 文件、783 项，约 87 秒；真实运行后 reader 网段小修只有定向 10 项测试（0.653 秒），不能混称最新全量已重跑。这些测试和实际内容失败并不矛盾。继续仅增加“提供了错误证据应拒绝”的测试，不会发现“完全不提供证据仍说出事实”。

## 9. 待评估方案，不预设结论

| 选项 | 可能收益 | 需要你评估的风险 |
| --- | --- | --- |
| 类型化事实块 + claim ID 引用，由代码渲染数字/状态 | 出处、状态和显示值有统一来源 | 如何防止旁边自由文本再补事实？如何处理自然语言中的非数字事实？ |
| 服务端拥有预算评估结果，最终回复引用已保存结果 | 消除无账本的金额保证，减少保存后漂移 | 成本缺项、币种、人数、范围、区间和未知应如何表达？ |
| 最终回复结构化，再由展示层组合自然语言 | 阻止任意回复重新引入事实和元叙述 | 会否过度模板化、损失有用说明？老 Artifact 如何显示？ |
| 有边界的语义审查/critic | 发现散文遗漏声明、语义冲突 | 本身可能误判且增加延迟费用，不能当真相来源或无限重试 |
| 冻结证据后比较模型或提示方案 | 区分生成质量与来源波动 | 更强模型也不应替代领域边界；尚无对照证据 |
| 分层 G1 与明确退出标准 | 避免基础链路成功和内容失败混称 | 哪些缺陷阻断产品放行，哪些只允许受控进入后续测量？ |

单纯删除英文、对所有内容加免责声明、替换东京某个票价、重复付费直到抽中好答案，都不能独立解决整体问题。另一方面，“验证所有自然语言真值”也可能不是可实现的 MVP 目标，需要你帮助界定务实边界。

## 10. 请重点回答的设计问题

1. 最小的事实合同应该约束哪些内容出口？模型能自由写哪些文字，哪些必须引用结构化 claim？请给出反例说明方案如何防止省略字段和改写绕过。
2. `source_observed`、当前适用、未来未知、冲突、无法访问应该如何建模？quote 包含 value 的机械检验之外，哪些语义需要人工/模型判断，哪些必须由代码负责？
3. 用户明确允许未知时，未绑定来源的具体数值是否必须删去，还是允许明确的参考状态？如何区分“参考”“估计”“已核实”，避免免责声明掩盖错误？
4. 没有完整成本时如何仍提供有用攻略，并禁止“符合预算”的无依据保证？请给出预算结构和判定规则。
5. `delivery.status=satisfied` 应维持领域完成含义，还是增加独立内容/证据状态？怎样避免两个状态互相冒充、避免模型自报质量通过？
6. 应如何保证最终回复与保存 Artifact 一致，同时保留自然表达？不希望仅用正则删除英文或数字造成无声信息损失。
