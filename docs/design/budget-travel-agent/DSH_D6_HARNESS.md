## H5 action runner

`backend/scripts/serve-dsh-d6.mjs` creates the isolated runtime. It requires an explicit loopback database URL, provider environment path, and historical ledger path. Each fresh invocation creates a random run directory, schema, loopback API/H5 ports, local-login key, D6 budget ledger and private manifest. The history link contains only the old ledger hash and counts; the old ledger is read-only and its authorization is not inherited. The H5 build uses a run-specific output directory and the run's loopback API URL. The run gate is closed unless `--execute` is present. The schema, D6 ledger, local-login key, manifest and built H5 remain after shutdown for cold restart/resume.

The provider environment supplies the current DSH route. The launcher verifies the configured DeepSeek model/search route without changing model, search, thinking, or max-token settings. For the isolated process it supplies a per-run JWT secret and a loopback Redis URL with Redis disabled; the JWT secret is private run state reused on resume so existing access/refresh tokens remain valid. These values satisfy shared schema requirements and do not enable another service. Optional `--places-url`, `--places-user-agent`, and `--places-proxy` arguments override only the isolated process's place-provider environment and are included in resume fingerprints. The D6 run uses these only when explicitly configured; live place lookup remains outside database transactions and is counted through the existing `place_provider_calls` lease. The D6 ledger is new, has unlimited monetary authorization as explicitly granted for DeepSeek, and still meters each call. Fare calls use the configured SerpApi fare provider and may be enabled only when `--allow-fares --fare-env <path>` is explicit; the launcher reads only `SERPAPI_KEY` from that separate file and records every fare-provider method/result status in the private run directory. It never loads the fare env over the DeepSeek environment or purchases additional allowance. Without those flags, fare methods are blocked.

Fresh server example (flags enabling fare calls should be included only for authorized fare journeys):

```powershell
node backend/scripts/serve-dsh-d6.mjs `
  --database-url 'postgresql://d6_test@127.0.0.1:58896/flightor_d6_validation' `
  --provider-env D:/path/to/current-dsh-env `
  --history-ledger D:/path/to/old-dsh-budget.json `
  --fare-env D:/path/to/app-backend.env --allow-fares --execute
```

## Commit observation contract

`backend/scripts/dsh-e2e-observation.mjs` records only commit submission shape: counts of item text objects, omitted day `cityId`, candidates missing `locationId`, selected `C-` aliases, and selected source aliases, plus validated replacement slots and whether base ID/content hash were omitted. It never records submitted prose, candidate/source references, or raw evidence refs. Accepted commits alone receive outcome counts for activity bindings and server-filled city/location identities, plus a boolean indicating server-supplied base/hash for slot replacements. Rejected commits record `accepted: false` and recognized revision reasons from cleaned `issues`, `presentationIssues`, and `repair.issues`, plus the controlled `error.revisionCode` and `error.details.code`; this supports both the current error shape and legacy `error.details` issues. Reason codes are restricted to values emitted by `travel-guides/validation.ts`, `travel-guides/finalization.ts`, DSH commit preflight, and the repair/publication allowlists. For parameterized `guide_research_type:<category>` issues, only `guide_research_type` is retained. Details, classifications, field paths, category suffixes, and unknown values are discarded. The fixture covers day coverage, duplicate evidence, raw-evidence preflight, the legacy shape, and rejection of private strings, URLs, UUIDs, and key-like values. Recovery records only finite non-negative `calls`, `argumentCorrections`, and `contentAttempts`, and an allowlisted `lastFailure` category. Web recording retains only `evidenceRefCount`; URLs have query and fragment removed. These are audit-shape observations, not proof that an accepted guide is correct or durably readable.

The focused fixture test runs a rejected commit followed by an accepted commit and asserts count fields, accepted-only completion fields, sanitized recovery counters, and the absence of raw text, private keys, and evidence references. An observer installed into a process before this version is loaded retains its older behavior; records from that process cannot verify this contract and must not be used as final count-only evidence.
