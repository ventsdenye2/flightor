## Evidence references

D6-18 successful fetch reuse: an exact requested HTTP(S) URL can reuse an available fetched body only within its existing `DshEvidenceStore` prepared attempt. The in-memory URL index re-reads the original scoped receipt and checks its body hash; it never enumerates historical generations or adopts a redirect-equivalent URL. Query parameters remain part of identity. A cache hit returns `cacheHit: true`, the original body and metadata, then binds the returned source aliases to the original evidence UUID, hash and retrieval time. Concurrent exact-URL fetches in the same store share the active safe-reader promise until a successful receipt is written; a later shared waiter returns `sharedFetch: true`, distinguishing a shared request from a persisted `cacheHit`. Same-URL receipt writes are serialized and compare response body/status/final URL/truncation before reusing a record. Failed/empty/challenge results are not cached. Each caller checks its own cancellation while waiting; the first caller's signal controls the underlying reader, so cancelling a non-owner waiter does not stop it, while cancelling the initiating caller fails the shared request and permits a later retry. No receipt is written until `__record_web` runs. Store replacement on a new turn or Trip-version advance drops the index. This avoids another safe-reader HTTP call; tool invocations and original source uncertainty remain visible. Source semantic applicability still requires reading the actual text, and a cache hit never establishes fact verification. The concurrent regression first reproduced two HTTP requests, then passed with the single-flight repair; its five focused reuse tests pass. Earlier four evidence/web/reuse files passed 23/23, service/web/reuse passed 19/19, check/build passed and the official fixture worker observer passed 1/1. These are scoped engineering checks; real final content and UI acceptance remain pending.

D6-19 source selection: the single main model's existing tool/persona contract now explicitly requires examining the actual returned text for each candidate, rather than treating a city/category page, URL/title or authority label as venue coverage. A name mention does not establish unwritten facilities, foods or visitor rules. Missing coverage requires targeted research or another supported activity while preserving requested days/interests. The whole-trip budget cannot silently exclude accommodation, major costs or participants. This adds no model, internal identity field, semantic classifier or deterministic fact-proof claim. The r11 generic category body did reach the model intact; that old accepted guide remains content-failed. Existing safe-reader/worker IO tests verify delivery and provenance, while real content review must assess whether the model follows the semantic contract.

Persisted evidence records keep their UUID identity and file layout. `DshEvidenceStore` continues returning `evidenceRefs` for compatibility and now also returns short `sourceRefs` for current-turn model input. Each short source token includes a digest of owner, Trip, conversation, generation and Trip-context version, plus the content hash prefix and a per-store sequence. The store resolves these tokens only through its in-memory alias map, then performs the existing exact-scope check against the persisted record. Reconstructing a store, changing generation/version, or presenting another turn's token does not grant access. Failed, empty, invalid, or challenge responses still produce no usable aliases.

Persisted research remains reusable through the existing `gc1` candidate reference. The D6 `DshReferences` helper can assign a short per-turn alias to such a reference. The alias maps back to the original `gc1` value, which still undergoes the existing owner/Trip/artifact/version/finding checks at the domain boundary. Aliases are scoped by owner, Trip, conversation, generation, and context version; they are not persisted and cannot be redirected to another finding.

The service/commit adapters expose current candidates through these helpers and resolve registered short aliases before the existing domain validation. Current-turn search/fetch source aliases resolve in `DshEvidenceStore.get`; persisted candidate aliases resolve to the original `gc1` reference before `commit_travel_guide` performs its existing owner/Trip/artifact/version/finding checks. Legacy full references remain compatible, but aliases from another turn cannot be resolved by a new registry.

## Location preparation

For city-only Nominatim jsonv2 resolution, `class` is the primary OSM category field and `category` is a compatibility fallback only when `class` is absent (`class ?? category`). A present but non-matching `class` is authoritative and cannot be overridden by a matching `category`. The parser then admits `place` city/town and `boundary`/`administrative` city/town-address records; all existing identity, exact-name, qualifier, country and coordinate checks still apply. The category-only administrative-city regression and bounded Kyoto smoke are tracked as D6-13 in the acceptance ledger.

Guide locations are identities, not free-form labels. Current Trip city identities and trusted locations returned by the existing resolver can seed the per-turn resolved-location ledger. A guide commit may select an identity already in that ledger; it must not turn an airport identity into a city or a POI, infer a new destination from candidate prose, or resolve an arbitrary attraction with the aviation resolver.

`uniqueSelectedTripCity` provides a deterministic preparation primitive when the Trip already has exactly one distinct selected city identity. Multiple selected cities, an airport identity, or no selected city remain unresolved. It performs no lookup or network request. Separately, aviation `resolve_location` queries with exactly `types: ["city"]` first check the local FlightOR city directory; only a local miss may use the configured Nominatim-compatible endpoint. That request asks for city features in the address layer and admits OSM `place` city/town or `boundary`/`administrative` city/town-address entities with a real `osm_type`, numeric `osm_id`, coordinates and `address.country_code`. The city portion must exactly match the returned `name` or `namedetails`; every comma-delimited qualifier must exactly match an OSM country/administrative address value. Returned country and `osm:*` ID are source data, not inferred aliases. Multiple results remain multiple city matches for caller disambiguation. Airport and mixed-type lookups retain the existing aviation-provider path, and this does not add POI fallback or hard-coded city names.

The fallback is enabled only when both the existing Nominatim URL and User-Agent are explicitly configured. It reuses the existing Nominatim HTTP transport/proxy, query-cache table, provider-call lease and cancellation signal. A local city hit creates no Nominatim request; an unconfigured fallback returns an empty, unverified result. The resolved OSM identity is available only through the current turn's trusted provider-result ledger; it does not rewrite a Trip's canonical city identity. This helper does not expand the Trip or change selected destinations automatically.

The PostgreSQL city-query cache locks the query key before updating it. When an unexpired valid entry and a later result disagree, distinct OSM IDs are merged up to the shared 20-match schema/provider limit; an existing record for the same OSM ID and its verification record remain authoritative. A later non-empty verified result may replace an unexpired empty result, because the empty entry carries no city identity to protect. These updates change only `result_json`, preserving the database expiry exactly and never extending the cache lifetime. Expired entries can be replaced normally. The isolated PostgreSQL regression at `backend/src/places/postgres.integration.test.ts` covers those cases plus two-connection request coalescing; its HTTP response is a controlled fixture, not live Nominatim evidence.

## Candidate temporal evidence

The compact D6 candidate may submit `{from, to, sourceRef, quote}`. `sourceRef`
must be one of that candidate's current `sourceRefs`; the service resolves the
scoped receipt and stores Research v2 `sourceUrl` rather than the compact alias.
Only a selected event candidate requires temporal evidence. Unselected events
may remain as findings without it, but supplied evidence is always validated.

Quotes accept complete ISO dates or one unambiguous CJK occurrence range. The
quote must exactly match retrieved snippet text or fetched body text whose
SHA-256 matches the captured hash. A fetched record with a bad body hash is
rejected even when its snippet matches. Recognized publication, update,
retrieval, expiry, and query-window labels are not occurrence evidence. These
checks bind and transcribe source dates; they do not establish that a sentence
describes the named event. The existing domain validator independently rejects
an otherwise supported event outside the Trip dates. No automatic slot or
schedule edit is performed.

## Compact Goal and Reference Contract

The model-facing D6 schema keeps source locators separate from candidate locators. New candidates require current-turn `sourceRefs` (short `s1.*` receipts or compatible evidence UUIDs from this same turn) and are registered by key; a scheduled activity selects exactly one distinct `candidateKey` or a persisted `candidateRef` returned by the current snapshot or this turn's `read_artifact`. Supplemental new candidates use `supportingCandidateKeys` and do not need activity text; supplemental persisted candidates use `supportingRefs` only. Persisted candidates are normally presented through current-preparation `C-*` aliases; compatible full `gc1` candidate references still pass through the scoped adapter and domain validation. URLs are not accepted as source or candidate references; evidence UUID and `gc1` compatibility does not make earlier-turn or unscoped data valid. Evidence `s1.*` aliases exist only in the active `DshEvidenceStore` index. After an accepted Trip version change the store is replaced, so aliases from the previous version resolve as unavailable (`null`) and never reach the file repository as paths; canonical UUID/SHA references remain supported and still undergo scope checks.

Every scheduled or supplemental new key must match an explicit `candidates[].key`; search/fetch receipts alone do not register candidates. A first new intent checks key coverage after the existing Goal runtime, kind, Trip snapshot and flight guards but before accepting or writing its Goal. An accepted Goal checks registration after the existing workspace-scope read and before research writes. Omitting candidates can reuse only the keys already registered in that prepared attempt and unchanged scope; a supplied list replaces the earlier list completely. Missing definitions return bounded registration status, missing/available keys and the candidates field, without matching webpage semantics or inventing candidates. There are no added database reads or model calls. Current source support, scope and publication checks remain required. The expanded eight-file regression passed 112/112; official fixture worker correction reused one search and the same scoped sources. These are deterministic/fixture results, not real H5 acceptance.

The first durable operation needs a new semantic `intent` matching the explicit current user goal. Ordinary raw-web reference-only material does not independently verify facts, so the first `travel_guide` Goal for that path must explicitly set `allowPartial=true`; this preserves partial-verification status and does not relax other Goal or publication checks. A user requirement for independent fact verification cannot be met by that path and must not be weakened. Before Goal acceptance, argument/prerequisite correction must provide or preserve the intent needed to accept the initial Goal. After acceptance, same-turn guide repair omits `intent`/`goalRef` and reuses its immutable constraints. Only an explicit Trip setter that returns persisted `satisfied` and advances the version ends its Goal binding; the next durable objective requires a new matching intent. Failed, pending, no-op setters, and guide content repair do not advance it.

## Prepared submission integration coverage

D6's compact schema keeps source selection distinct from candidate selection. Source URLs are rejected by the DSH reference schema, and the service does not remove malformed fields to turn a rejected command into a different submission. Legacy domain/API schemas are unchanged. An unavailable scoped candidate reference returns a safe field path and a prerequisite correction with the original bounded commit allowance; it consumes no semantic content attempt. Neither its raw reference nor arbitrary error details are copied into feedback. The exact source/candidate fields and Goal rules are stated above.

`preparation.test.ts` exercises the prepared submission through `adaptDshCommit` and the real `createCommitGuideTool`, not only the compact schema. Its first accepted submission omits city/location IDs when the Trip has one selected city, supplies per-candidate current-turn short `sourceRefs`, places activity text inside each day item, and retains the semantic `travel_guide` intent while omitting server-owned base ID/hash. It then binds the accepted base from a prepared snapshot and accepts a slot edit that omits base ID/hash, resolves a short persisted candidate alias, and proves the other slot and its accepted text remain unchanged.

After an explicit Trip setter advances the version, the service replaces the DSH evidence store. Previous-version `s1.*` aliases are therefore unavailable even within the same user turn; the caller must obtain fresh sourceRefs under the new snapshot. Unknown or malformed aliases resolve to `null` before a file-repository lookup, allowing the guide tool to return its bounded `candidate_evidence_unavailable` correction. Canonical UUID/SHA references remain eligible for repository lookup and still pass owner/Trip/conversation/generation/version scope checks. A corrupt record reached through a registered current alias continues to surface its integrity error.

The File repository controlled-update regression reproduced the prior failure before the fix: a stale `s1.*` alias reached `FileDshEvidenceRepository.get`, raised `TypeError: Evidence reference must be a canonical UUID or lowercase SHA-256`, and was exposed as `DSH_TOOL_FAILURE`. After the fix, the focused evidence/store and same-turn controlled-update suites passed 16/16; the stale source receives the bounded revision response and a fresh post-update source supports accepted publication. The SHA-reference regression stores a real current-scope evidence record under a canonical SHA key, confirms the complete record is returned, and confirms owner/version mismatches return `null`. This uses temporary file evidence and in-memory Trip/Goal/Artifact repositories, not the original runtime records or a database.

This is an in-memory domain integration test, not an AgentLoop, database, model, provider, or UI acceptance claim. The focused command `cd backend; npm test -- --run src/agent/dsh/preparation.test.ts` passed 6/6 on 2026-10-06. With the locked `@deepseek-ai/dsh-tools` and `@deepseek-ai/dsh-tool-web` `0.1.7-rc.1`, the `tools/post-execute` success result retains canonical `value`; `runtime.mjs` passes `result.value` to `__record_web`. The official web tool returns structured `value.sources` and projects the same sources to `meta.sources`. In the locked `@deepseek-ai/dsh-web-search-deepseek` `0.1.7-rc.1`, source items provide URL/title/page-age, while snippets are joined from citation text blocks keyed by URL; a successful search result does not guarantee citation text. `DshEvidenceStore.recordSearch` accepts only `result.sources`, requires a safe HTTP(S) URL, and marks a source without a snippet as `no_body`. `references()` exposes refs only for `available` records. Search prose or a URL alone is not a source snapshot and must not be promoted to evidence. The current operational path is to fetch a promising safe URL early, then use only a fetch receipt whose retrieved body is available; if fetch is blocked or has no body, try another retrieved source. No code or dependency change was made for this audit.
