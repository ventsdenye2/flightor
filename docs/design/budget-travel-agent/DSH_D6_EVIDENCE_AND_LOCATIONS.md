# DSH D6 Evidence and Locations

Status: implementation work in progress, 2026-10-06. This document records the current contracts and the D6 reference helper behavior. It does not claim end-to-end DSH integration or acceptance; see [D6 acceptance](DSH_D6_ACCEPTANCE.md).

## Evidence references

Persisted evidence records keep their UUID identity and file layout. `DshEvidenceStore` continues returning `evidenceRefs` for compatibility and now also returns short `sourceRefs` for current-turn model input. Each short source token includes a digest of owner, Trip, conversation, generation and Trip-context version, plus the content hash prefix and a per-store sequence. The store resolves these tokens only through its in-memory alias map, then performs the existing exact-scope check against the persisted record. Reconstructing a store, changing generation/version, or presenting another turn's token does not grant access. Failed, empty, invalid, or challenge responses still produce no usable aliases.

Persisted research remains reusable through the existing `gc1` candidate reference. The D6 `DshReferences` helper can assign a short per-turn alias to such a reference. The alias maps back to the original `gc1` value, which still undergoes the existing owner/Trip/artifact/version/finding checks at the domain boundary. Aliases are scoped by owner, Trip, conversation, generation, and context version; they are not persisted and cannot be redirected to another finding.

The service/commit adapters expose current candidates through these helpers and resolve registered short aliases before the existing domain validation. Current-turn search/fetch source aliases resolve in `DshEvidenceStore.get`; persisted candidate aliases resolve to the original `gc1` reference before `commit_travel_guide` performs its existing owner/Trip/artifact/version/finding checks. Legacy full references remain compatible, but aliases from another turn cannot be resolved by a new registry.

## Location preparation

Guide locations are identities, not free-form labels. Current Trip city identities and trusted locations returned by the existing resolver can seed the per-turn resolved-location ledger. A guide commit may select an identity already in that ledger; it must not turn an airport identity into a city or a POI, infer a new destination from candidate prose, or resolve an arbitrary attraction with the aviation resolver.

`uniqueSelectedTripCity` provides a deterministic preparation primitive when the Trip already has exactly one distinct selected city identity. Multiple selected cities, an airport identity, or no selected city remain unresolved. It performs no lookup or network request. Separately, aviation `resolve_location` queries with exactly `types: ["city"]` first check the local FlightOR city directory; only a local miss may use the configured Nominatim-compatible endpoint. That request asks for city features in the address layer and admits OSM `place` city/town or `boundary`/`administrative` city/town-address entities with a real `osm_type`, numeric `osm_id`, coordinates and `address.country_code`. The city portion must exactly match the returned `name` or `namedetails`; every comma-delimited qualifier must exactly match an OSM country/administrative address value. Returned country and `osm:*` ID are source data, not inferred aliases. Multiple results remain multiple city matches for caller disambiguation. Airport and mixed-type lookups retain the existing aviation-provider path, and this does not add POI fallback or hard-coded city names.

The fallback is enabled only when both the existing Nominatim URL and User-Agent are explicitly configured. It reuses the existing Nominatim HTTP transport/proxy, query-cache table, provider-call lease and cancellation signal. A local city hit creates no Nominatim request; an unconfigured fallback returns an empty, unverified result. The resolved OSM identity is available only through the current turn's trusted provider-result ledger; it does not rewrite a Trip's canonical city identity. This helper does not expand the Trip or change selected destinations automatically.

The PostgreSQL city-query cache locks the query key before updating it. When an unexpired valid entry and a later result disagree, distinct OSM IDs are merged up to the shared 20-match schema/provider limit; an existing record for the same OSM ID and its verification record remain authoritative. A later non-empty verified result may replace an unexpired empty result, because the empty entry carries no city identity to protect. These updates change only `result_json`, preserving the database expiry exactly and never extending the cache lifetime. Expired entries can be replaced normally. The isolated PostgreSQL regression at `backend/src/places/postgres.integration.test.ts` covers those cases plus two-connection request coalescing; its HTTP response is a controlled fixture, not live Nominatim evidence.

## Prepared submission integration coverage

`preparation.test.ts` exercises the prepared submission through `adaptDshCommit` and the real `createCommitGuideTool`, not only the compact schema. Its first accepted submission omits city/location IDs when the Trip has one selected city, supplies per-candidate current-turn short `sourceRefs`, places activity text inside each day item, and retains the semantic `travel_guide` intent while omitting server-owned base ID/hash. It then binds the accepted base from a prepared snapshot and accepts a slot edit that omits base ID/hash, resolves a short persisted candidate alias, and proves the other slot and its accepted text remain unchanged.

This is an in-memory domain integration test, not an AgentLoop, database, model, provider, or UI acceptance claim. The focused command `cd backend; npm test -- --run src/agent/dsh/preparation.test.ts` passed 6/6 on 2026-10-06. Windows sandbox execution required permitting esbuild's child process; without it Vitest exits before loading the config.

## Fixed Offline Replay

The [fixed replay script](../../../backend/scripts/d6-fixed-replay.mjs) runs the same two-day Tokyo guide with three distinct visits and one synthetic source snippet against the clean `f2ec6c1f75000d368d4d83b7ae6428c17dea3e0c` compiled baseline and the current compiled D6 tree. Baseline receives full days/text and legacy evidence UUIDs; D6 passes compact per-visit text through `adaptDshCommit` and current source aliases. Each sample uses fresh in-memory Trip, Artifact, Goal, and evidence repositories. One warm-up and ten paired samples run per version. The harness does not instantiate the AgentLoop, model, search or fetch provider, HTTP reader, or database.

Reproduce from the repository root:

```powershell
node backend/scripts/d6-fixed-replay.mjs
node backend/scripts/d6-fixed-replay.mjs --execute --baseline-dist backend/.demo/d6-baseline/backend/dist --current-dist backend/dist --output-dir backend/.demo/d6-fixed-replay
```

Run recorded at 2026-10-06 11:11 Asia/Shanghai: 10/10 accepted per version; all ten semantic guide projections matched; failures 0; model calls 0; external calls 0. P50 execution was 10.622 ms baseline and 10.252 ms D6. The D6 adapter measured 0.446 ms p50; total fixture time, including adapter, was 11.855 ms baseline and 12.027 ms D6. The 0.172 ms total difference is within this small in-memory run's timing noise and is not evidence of a user-visible speedup. Trip repository reads fell from 20 to 18 per sample; Artifact repository calls were identical (3 creates, 15 gets, 6 scoped gets, 2 Trip listings, 1 final-variant save). Every sample, method-call count, semantic projection and error is preserved in ignored output `backend/.demo/d6-fixed-replay/fixed-replay-2026-10-06T03-11-33.718Z.json`.
