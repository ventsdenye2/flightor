# 从交互体验重新审视架构

2026-09-20，补充用户对等待、个性化和既有 UI 接入的要求。本记录保留交互诊断；当前实施顺序已统一到 [DPS](DPS.md)，本页不再维护独立计划。

## 判断

当前交互执行路径偏重。问题不只是有多少模块，而是用户得到第一份可用结果之前，需要等待多少远端模型/研究步骤，以及等待时能否操作已有结果。状态隔离、真实报价、owner/version 和完成校验应保留；不能用删除可靠性边界换表面速度。

上一版计划过早把持久任务、完整窗口领域和攻略 v2 放到主线上，容易形成另一轮基础设施建设。应先用现有服务打通快速、可交互的纵向切片，再按明确必要性扩展。

## 设计改为三种响应节奏

### 1. 快速理解与回应

收到请求立即展示提交状态；Agent 尽快给出对关键条件的理解，以及一个必要问题或下一步行动。确定的结构化事实直接由卡片展示，不必等模型再写一段完整总结。

目标不是强行每条消息走一套固定工作流，而是允许 Planner 在信息足够时一次发出有用操作。用户只问解释/调整偏好时，不启动深度研究。

### 2. 可决策的首批结果

航班检索保存第一批有效候选后立即显示，用户可以看详情、比较和采用。扩展日期/更多候选可后续继续，不阻塞已得到的结果。界面明确“已搜索范围”，不把第一批最便宜称为全局最低。

采用航班后先交付符合已知到离时间的行程骨架，例如旅行日、可玩天数、城市分配及兴趣主题；骨架有自己的可见状态，不冒充已核验攻略。若已有合格地点资料，可一起呈现少量活动；若没有，明确待补充，不编景点事实。

### 3. 有边界的细化

围绕已选航线与用户关注的日期研究具体活动。营业时间、活动时段、交通与图片按需要补齐；照片失败不阻塞航班或文字日程。入境与赶飞机的关键事实未知时，相关中转活动保持条件方案，不能标可执行。

一份行程可以“航空骨架已确定、目的地日程可浏览、中转活动待核实”。分维度完成状态比一个全局 loading/ready 更符合真实旅行决策。

## 减少复杂度的具体方向

- 保留一个 Planner 和现有领域服务；不加总控 Agent、评价 Agent 或多层模型裁判。
- 评估把服务器已知的 Goal 生命周期记账收入现有工具/运行时内部；模型仍定义目标和选择工具，服务器负责创建执行记录与验收。只有确定可机械处理的部分才收回，不能用关键词自动恢复错误目标。这是需另行接受的契约调整，不是现在删除 Goal 工具。
- 减少“得到结构化结果后，再等模型复述才能显示”的往返。阶段结果通过当前轮询的 Artifact 引用增量传给 UI，先不用更换通信栈。
- 在已有 verified 来源缓存与当前数据覆盖上生成首版，只为缺失、易变、决定可行性的事实联网研究。缓存必须带日期/来源适用性，不能把旧报价当新报价。
- 前端允许浏览、排序、展开、编辑草稿；修改已执行条件时，明确取消/替代当前任务和版本边界。不能简单去掉 disabled 后让并发写入竞争。
- 时间目标分别测接单、首次有用回复、首批航班、可浏览日程、完整核验；不能拿动画出现速度当首次有效结果。
- 新队列/完整事件日志仅在重启恢复或多实例确有需求时进入实施。若开放后台持续运行，则必须同时补对应持久恢复能力，不能声称进程内任务可靠续跑。

## 对三项需求的交互要求

**等待：** 默认展示一句当前行动、已产生结果和下一步可操作入口；详细执行摘要可展开。不要默认用一大段所谓思维链占屏，用户更需要“现在有什么可选”。真实原因例如“你不接受夜间转机，已过滤这类航班”，必须由实际条件和结果支持。

**个性化：** 先用少量高影响条件——日期弹性、总预算、同行人数、兴趣、旅行节奏、中转容忍度。将 Agent 的理解做成可编辑标签；只问能改变推荐的问题。解释便宜方案对用户的实际代价，不把改文案当个性化。局部修改只影响相关选择；不每次重查整趟行程。

**地图图文：** 保留现有视觉，航班结果先出航线示意，活动结果到达后按天补景点。地图、日程和图片共用结构化 activity/place ID；点任意一处定位另一处。图片/地图细节按需加载，无真实数据时保留可读空态。
