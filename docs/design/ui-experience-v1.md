## 设计语言

海洋青白、轻杂志排版、清晰事实层级。规划、探索、航班搜索与比较、行程、收藏和我的等界面共用这套语言。旧 Phase 6 的 near-black 规范保留为既有页面的历史记录，后续视觉改版遵循本规范，按页面逐步迁移。

## 跨页面一致性

- 共用配色、字号层级、间距规则、线性图标、按钮、导航、标签、卡片与底部弹层；同一种操作在不同页面保持相同外观和反馈。
- 实景图片保持自然色调、明确主体与来源。目的地和探索内容可以用大图；输入、搜索、比较和设置页面按任务需要安排图片与信息密度。
- 白底留白与海洋青主操作贯穿各页，列表、表单和高密度航班信息保持清晰层级。布局随内容调整，避免把旅行详情的首图和段落结构机械复制到所有页面。
- 加载、部分结果、空态、失败、重试、选中、禁用和撤销使用共同的状态表达；来源、估算和未知项始终可见。
- 手机优先，主操作触控区至少 44px；微信与网页保持视觉和交互语义一致，地图、滚动、安全区等由平台适配。

| 页面 | 应用方式 |
| --- | --- |
| 规划与输入 | 清楚的输入层级、浅色分组、海洋青主操作；结果沿用同一套卡片和状态反馈 |
| 探索与目的地 | 实景照片、衬线内容标题、轻杂志排版；沿用相同收藏和详情操作 |
| 航班搜索与比较 | 延续票卡、对齐的时刻和价格、明确中转与来源信息，按比较需要提高密度 |
| 行程与活动详情 | 当前概览、每日行程、航班视图和活动弹层作为已认可的视觉参考 |
| 我的、收藏与设置 | 延续白底、浅色面板、线性图标和列表节奏，按功能组织内容 |

当前共用样式和组件由 `SharedUI.tsx`、`shared.scss`、`VisualMedia.tsx` 与 `experience.scss` 统一维护，避免各页面复制后各自演变。应用通过 `AppExperience.tsx` 连接主导航和二级页面，以下范围已实现为本地交互样稿：

| 页面/入口 | 组件与交互范围 |
| --- | --- |
| 主导航“规划” | `PlannerPage`：想法输入、建议填入、加载/取消/继续、固定示例结果、编辑与重新开始 |
| 主导航“探索” | `ExplorePage`：分类、搜索空态、目的地和灵感详情、来源、收藏、填入规划；目的地抵达信息弹层 |
| 规划中的航班入口 | `FlightExplorer`：表单校验、交换/日期/人数、固定结果、加载/取消/失败、排序、筛选、比较、航段详情、价格提醒 |
| 主导航“行程”与旅行详情 | `TripsPage`、`TripExperience`：列表、归档/恢复、新建；概览、每日安排、航班、活动查看/替换/移出/撤销 |
| 我的收藏、价格提醒 | `CollectionsPage`、`AlertsPage`：分组与空态、打开收藏、取消/撤销；提醒启停、改价、删除/撤销 |
| 主导航“我的” | `ProfilePage`：访客/演示登录、昵称、偏好草稿/保存、字号、隐私、关于、退出与清空收藏 |

既有 `index`、`search`、`route`、`hub-detail` 等注册页面的展示任务在独立应用中有对应界面，完整映射见 [交接文档](../UI_PHASE_HANDOFF.md#页面覆盖与代码入口)。本轮没有迁移 `src/app.config.ts` 的生产路由，也没有替换生产页面的业务实现。

## 信息结构

固定样例为：上海 → 多哈 → 里斯本，7 天。概览先给路线与总状态；每日行程按天展示城市、安排和来源；航班列表先呈现时刻、价格、航司与中转风险；详情以 bottom sheet 展开完整段落、来源、未知项和操作。

价格示例必须附“示例/估算”语义和来源。未知价格、未核验时刻、图片失败、部分生成应保留空态或警示，不能补猜。地图按照路线顺序讲述节点，并提供文本列表。

## 状态与动作

主要动作保持至少 44px 触控区：局部替换、删除、撤销、收藏。删除后提供可逆撤销；本版收藏仅在预览会话内保留，云端保存及版本冲突属于后续联调。部分结果显示已完成范围与待补内容；图片失败显示占位和重试，不影响文字行程。

跨页收藏和提醒由父应用持有，同一书签与“我的”数量保持一致；提醒只演示设置，不监测票价或通知。二级页面使用返回栈，收藏进入详情、提醒进入航班后返回来源页面，并保留栈内局部状态。普通主导航切换保留规划会话，“新建行程”明确开启空白输入。

偏好编辑与已保存值分开：未保存返回不改变首页摘要，保存后更新本次预览的偏好。昵称、收藏、提醒、偏好和演示登录状态均为当前页面运行态，刷新或重置后清除；界面中的登录展示不获取真实身份。

## 组件策略

`AppExperience` 持有页面栈和跨页演示状态，页面组件负责本地表单、编辑草稿、筛选和详情状态；旅行详情可通过 props 接收固定每日行程。组件不请求业务 API、不解析自然语言或写入业务 stores。规划结果、航班和目的地概览仍使用固定示例，任意输入不会被当作已生成真实结果。

Taro 与 Vite 共享 feature，网页对基础组件、Input/Textarea 事件及地图做平台适配，微信使用独立入口。胜出方案接入真实数据时，再完成展示数据字段映射、来源和 unknown 状态；UI 的视觉完成不决定模型/架构评测结论。

扩展后的网页与独立 Taro 类型检查、生产构建均通过。浏览器除原旅行详情的日期、活动、修改与失败状态外，本轮还在 390×844、320×740 检查新增页面，实际操作搜索空态、收藏/撤销、跨页返回、航班校验/排序/比较/筛选/详情、提醒增改删撤销、偏好草稿与保存、昵称、字号、隐私、退出和关于。
