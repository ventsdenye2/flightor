## 1. 产品主流程：先选航班，再规划游玩

FlightOR 的核心价值是帮助用户比较不同航空路线和转机方案，在票价、总耗时、等待、风险与偏好之间做取舍，不是先生成一篇泛旅行攻略。

默认主流程为：

```text
用户描述旅行需求
→ 补齐必要的出发地、目的地、出发日期等搜索条件
→ 查询真实航班，并用现有推荐/路线引擎筛选与比较
→ 展示多个可供用户选择的航班或航空路线
→ 用户查看详情、比较、明确确认采用其中一个方案
→ 服务端持久保存这次选择
→ 根据已选航班和用户意愿，安排目的地及适用的中转地游玩
→ 显示关联航班、转机和每日活动的完整行程
→ 用户修改，结果可保存、刷新恢复
```

以下不是合格实现：先生成攻略再附几张航班卡；默认把排名第一当作用户选择；点开详情就宣称已采用；只在本地变量中保存选择；游玩路线与已选航班没有实际关联。

这是用户决策顺序，不是要将整个 Agent 改成死板工作流。查询和研究阶段仍由现有 Planner 自主选择必要工具；确定性服务负责事实、排序、权限和时间约束。不得为此新建另一套 Agent Runtime 或多 Agent 框架。

本次新增的是默认的“航班优先”路径。保留已有单独查航班、明确“只做游玩攻略”的合法用法；不要把所有旧攻略接口一刀切成必须先查票。已有自订航班入口若存在可复用，本轮不扩张到机票文件识别等功能。

## 4. 第一阶段：正式前端先打通可操作流程

### 4.1 需求输入与航班推荐

保留已有布局、字体与蓝色主题，不开展新一轮视觉重设计。主输入文案应明确表达“先比较航班，再安排行程”。搜索开始前只补齐必要信息，不让用户填一张大而全的旅游问卷。

航班结果在当前规划流程内直接可达，不要求绕到“我的行程 → 对话与结果”才能找到。手动搜索和 Agent 返回结果最终应复用同一套候选展示、详情和采用动作。

候选卡优先清楚展示：

- 航空路线及完整中转机场链；金额、币种、单程/往返和人数口径。
- 总耗时、每次中转的等待时长、当地出发/抵达时间及跨日标记。
- 航司联程/自行中转、过夜、换机场等已知事实；未知行李和保护条件不能被写成“已保障”。
- 简短具体的推荐理由与取舍，不显示假 AI 分数、空洞标签或无依据“全球最优”。

提供综合推荐、价格优先、时长优先以及现有可用筛选。筛选和排序基于同一份结果在本地完成，不每点一次就重新请求付费 API。推荐标签必须能追溯到对应的实际排序或优化逻辑，不能把普通列表排序冒称 Pareto 优化。

有几条真实候选就展示几条，不为凑“经济/均衡/舒适”三个版本造数据。没有直飞报价不显示虚构的直飞对照价或节省百分比。显示金额时不要把单人单程报价包装成两人往返或旅行总预算。

### 4.2 查看、待确认和正式采用必须分开

点卡片可以展开详情或设置待确认候选，但不触发游玩规划。

在详情/确认区域设置明确动作，例如“采用此航线，继续规划”。确认区展示完整路线、价格口径和重要转机提示；中转游玩偏好可以放在这里，不必新增多层确认弹窗。

用户确认后：

- 禁止重复提交；先完成服务端保存，再推进到游玩阶段。
- 展示固定的“已选航班”摘要及“更换航班”入口。
- 保存失败时不显示成功、不启动依赖该选择的攻略任务。
- “采用”仅指用于规划，不是已购票、已预订、锁价或获得行李保障。

新主流程中，用户未确认采用前，不启动正式游玩攻略生成。采用后可继续发起规划；需要补齐的游玩天数/中转意愿在紧邻的同一流程中处理，不把用户丢回空白聊天首页。

### 4.3 游玩结果要看得出来自哪一班飞机

结果按“已选航班 / 中转安排（适用时） / 目的地每日安排”组织，仍复用现有详情页和组件。

提供清晰的正在生成、部分完成、失败重试、历史结果状态。再次提问、刷新或切页面不应导致已有候选、选择或结果消失。展示依据 workspace、有效选择和已保存结果，不只看最后一条消息。

可以在这个前端阶段使用明确标记的测试 fixture 或已有真实快照验证状态，但这不算真实闭环完成；不能把临时 fixture 变成正式接口失败时的静默兜底。

## 5. 第二阶段：选择持久化与航班—游玩绑定

### 5.1 最小必要的持久化改动

先复用现有 Trip/workspace 与 `savedRoute`。若现有结构只能保存优化路线，不能保存用户直接选择的报价，在当前领域模型里做小型兼容扩展，不要为保存一张机票强迫所有查询走一次重型路线生成。

允许统一的选择记录支持两类来源：

```text
报价选择：flight_search artifact + offerId
路线选择：optimized route_set artifact + routeId
```

具体字段名称自行沿用项目规范，避免新建多套相互不一致的 selectedFlight 状态。禁止把报价人为包装成一个假的 `optimized_routes` Artifact 来绕过校验。

服务端只接受来源引用和必要用户选择，从真实 Artifact 恢复价格、航段、机场与时间；不信任浏览器提交的“更便宜价格”或自行修改的时刻。验证 owner、Trip、Artifact 类型、候选存在性、版本及兼容条件。

采用动作应有明确用户授权、幂等与并发保护。区分 Trip 的更新版本和行程条件版本，避免一次纯选择动作无意义地使所有查询快照失效；真正改动日期/机场时仍保留原有版本检查。

### 5.2 游玩规划必须读取已选方案

启动游玩规划时，由服务端读取采用的真实快照，传给现有 Planner/研究与保存服务。至少包含全部航段、抵达和离开时间、每次转机窗口、已知时区及用户停留偏好。

保存的游玩结果必须能追溯到相应的选择、来源快照和选择修订号。不能只靠一段“用户选了 A 航班”的自由文本关联。

飞行、必要衔接和游玩在同一条时间逻辑上：目的地活动不能早于抵达后可用时间；结束日不能排到离开之后；首日按实际抵达时间安排，不强行塞满一天。

已有 `timeOfDay` 粗粒度结构不足时，按需要增加兼容的时间窗口/交通段引用；不要先造一个完整通用日历引擎。不能把“上午/下午”标签当作已经经过精确时间校验。

### 5.3 更换航班与恢复

更换已采用航班后，依赖旧选择的攻略必须标记需重算或明确不再适用，旧快照作为历史保留。旧任务迟到返回时，不得覆盖新选择或冒充当前攻略。

刷新页面、重新打开同一 Trip、退出再登录，应恢复已选路线和正确结果。重复点击只产生一次有效采用和一次对应规划，不重复消耗供应商调用。

若为用户新增游玩偏好导致 contextVersion 更新，按已有来源兼容与校验规则处理，不能通过重写旧快照版本跳过检查。可以不重查的航班不应因纯视觉或备注编辑被迫重查；无法证明兼容时明确失效而不是暗中复用。

## 6. 中转地游玩：可选、时间受约束、保留不确定性

这不是“凡是转机都生成景点”。要同时看用户是否希望停留、真实衔接窗口以及出机场与返回是否具有可评估条件。

1. 从已选完整航段之间提取所有中转，不只读取第一个 hub。供应商联程可能以一条完整 edge 保存，也必须读取内部 segments 和 layovers。
2. 区分中转、过夜、换机场和自行中转。未知等待时长不能按 0 处理；航司联程也不自动代表行李直挂或保护已核验。
3. 中转较短或用户不想出机场：安排机场内休息/用餐等轻量建议，不能生成市区游玩。
4. 有较长窗口且用户明确愿意：提供“安排中转地游玩”选项，展示时间窗口与必要前提，默认不擅自替用户勾选。
5. 可用游玩窗口要扣除下机/入境、机场往返、值机安检/登机和安全余量。来源不全的时长标注为假设或待确认，不输出虚假的精确可行结论。
6. 时间计算用带时区的真实时间或可靠 UTC 时间，显示用地点当地时间；覆盖跨日、多次转机和不同机场时区。禁止用浏览器当前时区直接相减。
7. 用户资料或入境条件不足时，不声称免签、必能出机场、一定赶得上。可以展示“满足入境与时间条件后可考虑”的暂定建议，不能计入已确认可执行日程。
8. 同一天跨中转城市和目的地时，用最小兼容扩展表达实际顺序，不凭空增加旅行天数，也不要将中转地强制加入最终 visit 列表导致整个航空路线重算或触发现有多目的地限制。

本轮不建设全球签证规则引擎。已有真实停留窗口内的小型、保守、可解释的安排即可。

长停留样本若本次实查没有返回，不延长实际航段时间、不虚构中转点。可用单独标明“测试样例”的 fixture 覆盖中转游玩交互，并把这一分支未获真实验收写清楚；不得混进真实查询快照。

## 8. 第三阶段：北京 → 里斯本真实跑一次

先完成前述正式交互与必要后端改动，再执行受控真实验收。沿用现有本地配置、真实 Provider 和专用演示数据库，不要求用户重新配置已经存在的密钥，不把密钥输出到聊天或报告。

基准案例：

```text
出发：北京；初次实际查询固定为 PEK，并向用户明确“北京首都”
目的地：里斯本 LIS
初次出发日期：2026-10-02（若执行时已过期，改为未来日期并记录）
航空范围：先验收去程、经济舱、CNY
偏好：经济实惠，但同时比较总耗时、中转等待和风险
中转意愿：存在合适窗口时可考虑停留游玩，不要求虚构某个 hub
游玩：在真实抵达之后安排里斯本；输入应清楚区分出发日、抵达日和游玩天数
```

本例不固定必须经多哈、迪拜或其他城市。由真实返回决定。先验收去程不代表可以删掉原有往返搜索功能，也不得把当前单向路线引擎包装成完整往返优化。

真实测试顺序：

1. 检查后端、数据库、必要 Worker、实际前端构建身份与模式；health/configured 只说明启动/配置，不说明供应商已实查成功。
2. 从正式的需求入口或它实际调用的同一领域服务发起真实航班查询；核对是非 mock provider。
3. 保存供应商脱敏返回及完整标准化快照。执行现有筛选/排序；要验收优化引擎时，另记录实际执行层级，不把排序当作完整优化。
4. 在正式前端查看多个真实候选，切换排序，展开转机详情，再点击确认采用。
5. 真实测试中的“用户选择”由测试浏览器明确点击一个候选产生。脚本可使用写明的测试选择策略，但应用自身不得默认确认第一条。
6. 确认采用已持久保存，随后才调用真实 Planner/研究服务生成游玩路线，验证已选航班输入被实际读取。
7. 校验抵达时间、中转安排、每日活动与选择绑定，再刷新、离开并重新打开验证恢复。
8. 导出这次真实链路的结果快照和状态记录，供之后拍片回放。

为控制额度，优先一次精确航班查询。仅在失败或候选不足且原因明确时针对性补查；默认本轮真实航班查询最多 4 次，完整攻略真实尝试最多 2 次。每次请求记录用途、供应商和结果，不把这一上限理解为必须用满；已有研究任务扇出和并发仍遵守现有上限。超过需要另行明确授权，不能自动扩大。

先尽可能通过离线单测与已有快照修复错误，再进行下一次付费验收。不要为截图、排序、刷新或重复演示重新付费查询。

供应商失败、余额/权限不足、真实返回为空或攻略 partial 时，如实记录。完成其他可以完成的部分，保留失败证据，不伪造成功、不把纯 fixture 命名为真实验收数据。

## 9. 真实快照 → 可重复回放

以后用于拍片的“mock”优先指本次真实结果的受控回放，不是重新编造航班、价格与攻略。

明确区分三种运行方式，尽量沿用现有配置体系而不新增复杂框架：

```text
live：正式代码 + 真实后端 + 真实供应商，获得并保存证据
replay：同一正式 UI + 真实快照回放，不重新调用业务付费 API
fixture：仅用于开发与边界测试的人工数据，明确标识，不能冒充 live
```

回放应在请求/数据适配边界完成；不能只给结果页硬塞一张成功卡。应用仍执行真实点击、选择、筛选与页面切换逻辑，回放层返回对应捕获的数据。回放属于 UI/快照验收，不等于又跑了一次真实后端。

数据包至少保留：

- 本次代码 SHA、dirty 状态/指纹、运行模式、查询参数、真实采集时间及票价 `checkedAt`。
- 供应商脱敏原始返回、标准化报价、实际比较/优化结果、未通过原因和 warnings。
- 全部实际候选及采用的 offerId/routeId、关联 Artifact、Trip/Conversation 与版本映射。
- 中转窗口、用户停留选项、采用动作、生成请求和与选择绑定的攻略结果。
- 足够恢复界面的 workspace 快照、必要接口响应，以及通过/失败、模型与 provider 调用情况。

已具备含义的时间戳、价格和来源不可重写。导出涉及身份 ID 时用明确且一致的脱敏映射，保留引用关系；测试/回放身份不得反向写入正式数据库。

不导出 token、Cookie、Authorization、供应商密钥或含敏感查询参数的 URL。原始素材和供应商数据先保留本地忽略目录；公开或提交前另行审查隐私和供应商授权，不把整个 `.demo` 目录加入 Git。

为数据包生成 manifest 和内容哈希。回放界面明确标示“真实查询快照 / 采集于……”，不重新声称为当前实时报价。允许地图资源单独联网，但不能让业务 API 回放未命中后偷偷调用真实供应商；不认识的请求应显式报错。

已有快照不足以覆盖完整流程时，列出缺失请求，不能混入不同日期或不同用户行程来补齐。

## 10. 验收：逐层说明什么真的跑通

先验证正式前端，再验证完整数据链。禁止仅用构建通过、服务健康检查或 `src-demo` 截图宣布完成。

### 必测交互与不变量

1. 有航班结果但无攻略时，规划入口仍展示候选与明确下一步，不出现空白成功页。
2. 未采用航班时，新主流程不会提前生成游玩攻略；查看详情不等于采用。
3. 同一真实结果可筛选、排序、查看全部转机；这些动作不会重复请求供应商。
4. 确认采用实际持久化；刷新/恢复后选择不丢失；保存失败不启动攻略。
5. 报价选择和优化路线选择都走正确来源；不伪造 Artifact 类型，不接受跨用户、跨 Trip 或不存在的候选。
6. 规划实际使用已选时间与停留意愿；首日、中转和离开日不与飞行/必要缓冲重叠。
7. 短中转、长中转愿意游玩、长中转拒绝、时间/条件未知都能得到相应且诚实的状态。
8. 更换航班使依赖的攻略正确失效；并发旧结果不会覆盖新选择。
9. 失败、partial、限流、取消和重试保留已有结果，不自动篡改成完成；重复提交幂等。
10. replay 可操作并可恢复，业务付费调用为零；fixture 与真实快照明确分离。

### 平台与视觉

H5 检查手机尺寸的真实产品入口；微信使用正式构建并实际查看模拟器，核对项目路径、`miniprogramRoot` 和 build-info。至少检查规划、航班比较、详情、采用后摘要和每日行程。

截图应能证明蓝色主题、长内容布局、底部白底、弹层和导航没有回归。H5 通过不等于微信通过；模拟器通过不等于真机通过。开发者工具服务端口未开启时如实说明不能自动操作，不声称已经刷新。

自动化测试尽可能覆盖接口、版本、并发和时间边界；跑现有相关类型检查与回归测试。不要用修改测试预期掩盖真实行为错误。

## 11. 执行顺序与最终交付

按以下顺序落地，而不是先把整个后端推倒重构：

```text
A. 保护现场并把正确的蓝色主题/文案/布局修复落实到 main
B. 正式前端跑通：需求 → 航班候选 → 查看/确认 → 已选摘要 → 游玩结果
C. 补齐选择持久化、Planner 输入绑定、中转时间约束与恢复
D. 真实查询并跑通一次采用后规划，保存快照
E. 验证真实快照回放，提交可回滚代码和验收说明
```

每完成一个阶段，简要说明改了什么、实际验证了什么及下一步。不要在 A/B 做完后自行结束，也不要恢复录制宣传片。

最终交付：

- main 上的相关提交、工作区和构建身份；仍未提交且保留的内容单列。
- H5 访问方式与微信当前应打开的正确项目/产物目录，附关键界面截图。
- 简明的前端交互流程与必要的服务端契约变更说明。
- 真实测试请求、实际返回数量、采用方案、游玩与中转结果、持久恢复证据。
- 本地脱敏快照包、manifest、真实采集与回放命令；注明调用次数、已知费用或费用未知。
- 验收矩阵，分别标出前端、后端、真实 Provider、微信模拟器、真机、地图、中转游玩分支是否真正验证。

更新一份集中维护的 `docs/FLIGHT_FIRST_ACCEPTANCE.md` 即可，不为每一步堆一批重复交接文档。在旧录制文档顶部注明“暂停：以航班优先产品闭环为先”，不删除历史要求。

任务的完成标志是：用户在正式产品中能看到真实航班选择，明确采用后获得与航班衔接的游玩安排，结果可恢复，并且这次真实结果已留存供以后回放。漂亮的演示壳、虚构的价格或成功文案不能替代上述事实。
