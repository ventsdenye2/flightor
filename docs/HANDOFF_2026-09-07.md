## 已暴露的架构问题

1. Planner 模型被要求复制完整 `LocationRef`、记住同轮解析前置条件并编排多个中间 Artifact。遗漏一步会触发付费工具重试并耗尽预算。
2. 攻略生成需要模型依次完成目的地集合、日程路线、研究和保存。模型可能只返回计划文字，或者在研究后超时，导致没有 TravelGuide Artifact。
3. 东京研究使用城市代码 TYO，路线使用 NRT，原始匹配把它们当作不同地点。已补回归并加入 TYO→NRT、OSA→KIX 映射，但应继续收敛为共享 Location Identity 服务。
4. 研究合成失败时，原始搜索摘要曾被提升为可用攻略条目，可能把旧展览带入未来行程。现在原始摘要统一标记 unverified，不可进入攻略；严格结构化合成保留服务器侧来源索引校验。
5. 新会话曾因模型只解析 NRT、未解析 PVG 而连续搜索失败。错误提示补丁能缓解，但最终设计应由 fare 领域边界按 IATA 解析并验证两个机场。
6. 当前 runtime 的 `requiredSuccessfulTool` 和 cloud service 的中文正则属于临时完成条件补丁，必须由领域工作流的持久化结果替换后删除。
7. SerpApi Research 中东京专用官方域名过滤属于演示期局部策略。ADR 0010 要求移除城市特例，改为通用来源策略或可配置策略。

## 质量门槛

接手后先做设计审查，再继续写代码。当前未暂存的领域服务只是方向性骨架，可以重写；不得为了保留已有代码而接受错误抽象。最终方案必须同时满足：

- 依赖方向只能是 Agent Tool → Application Workflow → Domain Service → Repository/Provider；领域层不得依赖 Agent runtime、HTTP route 或模型消息。
- Location Identity、Artifact 读写、Trip version/cancellation、Research verification 各只有一个权威实现；禁止跨工具复制规则。
- Application Workflow 使用显式输入/输出和稳定错误码，不用中文关键词、提示文本、调用次数或模型措辞判断业务完成。
- 模型只表达用户意图和解释结果。机场、价格、来源、行程状态、Artifact ID、版本与完成状态都由服务端建立和校验。
- 工作流写入必须具备一致性语义：冻结 context version、每个外部调用后重新检查、最终写入前再检查；部分成功留下可审计 Artifact，并返回结构化 partial/failure 状态。
- 通用机制不得包含东京、NRT、中文攻略关键词或单次演示数据。目的地/来源策略通过通用接口与配置表达。
- 测试围绕领域不变量和失败模式，不镜像实现。至少包含 provider 成功/部分失败/超时、取消、版本漂移、重试幂等、cross-owner、未知 IATA、来源不匹配和空覆盖。
- 性能预算由工作流定义：有界外部调用、可并行的只读请求并行、无意义重试为零；日志仅含 request/step/provider/duration/error code，不泄露提示、用户内容或密钥。
- 在提交前删除被新架构取代的临时补丁与死代码，运行依赖边界检查、TypeScript、全量测试和在线 E2E，并由 diff 审查确认没有两个并行实现长期共存。
