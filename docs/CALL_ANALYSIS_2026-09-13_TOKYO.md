## 4. 三次研究分别发生了什么

### 第一次：返回了内容，但不符合接收合同

第 60 次请求正常返回 HTTP 200，结束原因是 `stop`。研究审计记录的实际错误为：

```text
NATIVE_RESEARCH_OUTPUT_INVALID
Native research response had unsupported fields
```

原始内容中的 JSON 可以提取出来，其顶层字段为 `schemaVersion`、`findings`、`clarifications`。当前接收合同允许 `disposition`、`uncertainties`、`findings`；因此多出的 `schemaVersion` 与 `clarifications` 触发了顶层字段校验。这里不是请求超时，也不是 JSON 完全无法解析。

继续检查原始数据还发现：8 个 finding 中仅第一个带 `destinationIndex`，其余 7 个缺少该必填字段。实际执行首先停在顶层字段检查；缺少目的地索引是进一步的离线核查发现。不能声称“删掉两个多余字段就一定可以挽救这 27.628 秒”，更不能在没有明确映射规则时替模型补齐事实关联字段。

### 第二次：兼容工具成功交付四条研究结果

第 61 次 Planner 请求切换到 `web_research`。它仍使用同一个 Qwen 联网研究适配器，没有切回旧 SerpApi 搜索服务。第 62 次研究耗时 13.917 秒，审计状态为 `succeeded`；转换记录是 `extract_final_fenced_json`，接受 4 条结果：

| finding 后缀 | 类型 | 内容概括 | 证据状态 |
| ---: | --- | --- | --- |
| 0 | activity | 浅草寺与浅草文化步行 | partially_verified |
| 1 | activity | 上野公园与阿美横街 | partially_verified |
| 2 | practical | 东京餐饮、门票预算建议 | partially_verified |
| 3 | practical | 步行、地铁和交通卡建议 | partially_verified |

结果来源是供应商返回的 URL 引用和网页片段，包含旅游指南、旅游博客及旅游机构页面。适配器检查引用关联并保留片段证据限制，没有将它们升级为完整事实核验。没有证据表明此轮逐一核查了 2026 年相应日期的营业时间、门票、交通耗时和货币换算。

### 第三次：限流，而且不是修复索引错误所必需

第 63 次保存已经指出本地引用索引有误。随后 Planner 在第 64 次请求中决定重做研究，导致第 65 次 Qwen 请求。该请求在 1.157 秒内返回 429，未产生新研究产物。现有四条研究结果在随后两次修正保存中被直接复用并成功交付，证明本次保存问题可以用已有资料处理。

与这段路径直接相关的三个外部请求——决定补充研究（11.257 秒）、被限流的研究（1.157 秒）、决定读取已有材料（18.751 秒）——累计 **31.165 秒**。这是一个可定位的改进区间，不是保证能够全数消除的净节省：改进后的规划决策仍然需要时间，必须通过对照测试确认收益。

### “研究请求次数”和“联网搜索次数”不能混算

两次 HTTP 200 回执都报告：

```text
usage.server_tool_use_details.web_search_requests = 6
tool_calls_requested = 6
tool_calls_executed = 6
```

因此，本轮可确认的是 **3 次外层研究请求，以及成功 HTTP 回执中合计 12 次供应商报告的搜索请求**。第三次 429 没有相同使用量回执，不能据此认定实际总搜索数恰好为 12。

保留的研究请求参数同时设置了 `max_uses=2`、`max_tool_calls=2`、`max_results=5`、`max_total_results=10`。参数上限与回执计数不一致；当前证据不能证明二者采用同一计数单位，也没有供应商内部执行日志。当前实现接受合法范围内的报告计数，没有校验其是否超过这次请求声明的上限。应核查参数是否被执行，以及搜索计数、工具次数、批量查询各自的定义，不能继续把“最多两次搜索”作为已经验证的事实。

## 5. 为什么保存了三次才成功

这部分不是依据模型对错误的自述来猜测。核查使用了第 63、67、68 次回执内的原始 `save_travel_guide` 参数，并读取本次 run 的上下文、Goal 参数和研究产物，调用真实 `saveAuthoredTravelGuide` 做离线回放。数据库事务为只读；保存操作替换为纯内存仓库，没有写入业务数据库。

当时已接受的 Goal 限制包括：最多 1 个城市、最多 6 条结果、允许部分核验，并要求 `activity` 与 `practical` 两种类型都被覆盖。

| 保存尝试 | 实际输入问题或改动 | 回放结果 | 本次线上是否有攻略产物 |
| --- | --- | --- | --- |
| 第 63 次模型请求后 | `researchArtifactIds` 只有 1 项；第一天 `researchIndex=0`，第二天却为 `1` | `needs_revision`，`guide_research_index`；零次内存写入 | 无 |
| 第 67 次模型请求后 | 两天都改成 `researchIndex=0`；只选了两个 activity finding | `needs_revision`，`guide_research_type:practical`；零次内存写入 | 无 |
| 第 68 次模型请求后 | 保留两个 activity，并给第一天加入交通 practical、第二天加入预算 practical | `saved`；内存回放产生路线和攻略两项记录 | 有，目标攻略 ID 与截图一致 |

`researchIndex` 指向的是 **`researchArtifactIds` 数组的位置**，`findingId` 才用于选择该研究产物中的具体条目。本轮只有一份研究产物，所以所有条目的 `researchIndex` 都应为 0。第一次把第二个 finding 当成第二份研究产物，导致越界。这不要求新增联网研究。

第二次已经修正索引，但“在 notes 中写预算和交通建议”不等同于在攻略的选中证据中覆盖 practical 类型。校验器检查的是选中 finding 的类别。第三次加入对应 practical 条目，才满足当时 Goal 的覆盖合同。

对话工具追踪中前两次保存显示 `status=success`，含义是工具正常执行并返回结构化结果；其业务结果实际上是 `needs_revision`，且 `artifact_ids` 为空。诊断和前端都不应把工具执行成功直接解释为攻略保存成功。

## 7. 429 的原因：能确认与不能确认的部分

本次可以确认：

- 429 来自第 65 次外部 Qwen 研究请求，经 OpenRouter 返回；本地代码将其识别为 `PROVIDER_RATE_LIMITED`。
- 错误正文为 `Provider returned error`，`provider_name` 为 null，保留的响应头没有 `Retry-After`。服务端因此采用默认 30 秒冷却，阻止冷却窗口内重复研究派发。
- 本轮在此之前已经有两次 Qwen HTTP 200，并非研究服务整轮都不可用。
- 10:08:47 的只读账户快照显示非免费账户、Key 没有单独消费上限。该快照早于本轮约 19 分钟，不能替代请求发生时的所有供应商配额状态。
- 本次研究请求明确为 `allow_fallbacks=false`；遇到上游问题时，没有启用同一模型在其他供应商间切换。

仍不能确认具体触发的是请求频率、token 配额、并发、供应商容量、网关限制还是搜索服务限制。回执没有提供可定位的供应商及限流规则，也没有证明“账户余额不足”或“我们自己点击过快”就是原因。账户响应中的旧 `rate_limit` 字段明确标记为 deprecated，不能用它证明无限速。

关闭 fallback 可能影响可用性，但不是本次 429 的已证原因；是否启用需要在同一模型、同一任务下做对照，保留供应商路由及成本记录。

## 8. 当前信息搜索路径是否已经证明最优

当前实际链路为：

```text
DeepSeek Planner
  → research_destination 或 web_research
  → 同一个 NativeResearchAgent
  → OpenRouter 上的 Qwen 3.8 Flash + Exa web_search
  → 结构、引用、证据状态校验
  → 研究产物
  → DeepSeek 选择每日活动
  → 保存校验、完成检查、最终答复
```

本轮没有使用旧 SerpApi 路径。`research_destination` 与 `web_research` 是不同的 Planner 工具入口，但不能将它们视为两个独立搜索供应商，也不能把第二次成功归因于“换掉了 Qwen”。

Qwen 的选择有组件实验依据，但 **DeepSeek + Qwen + 当前工具流程尚未被证明是完整任务最优组合**。首轮实验中，Qwen 与 GLM 的 16 个样本经普通函数转换后均为 15/16 契约通过；研究调用中位数分别为 20.25 秒、25.31 秒。这是结构合同指标和研究组件耗时，不是攻略事实正确率、预算准确率或完整任务成功率。

实验还存在这些比较边界：每案例每模型仅一次，没有稳定的 p95 与方差估计；DeepSeek 的 thin-web 组只完成 2 例，完整三架构矩阵没有补齐；旧方案、直接联网、结构化联网的输入与搜索来源存在差异；人工内容量表尚未形成全量盲评。实验允许同一模型跨供应商 fallback，而本次集成关闭 fallback，配置也不是完全相同的对照。

本轮 129.758 秒中只有 42.702 秒属于研究请求，其余主要是 Planner 的多次决策与修正。即使单次研究能稳定达到实验中位数，也不能把整轮攻略耗时直接等同于 20 秒。完整实验说明见 [模型与后端研究架构首轮报告](experiments/model-architecture-results-2026-09-13.md)。

## 9. 优化建议、优先级与可测指标

以下是针对本次事实提出的下一步工作，不代表已经实施，也不承诺未经实验的固定提速比例。应先用归档回执验证，再安排独立的真实案例对照，避免用同一失败样本的修复结果直接宣布全局最优。

| 优先级 | 建议 | 本次依据 | 验收指标 |
| --- | --- | --- | --- |
| P0 | 让保存输入直接使用研究产物 ID，或为 `researchIndex` 增加逐条字段说明和可定位错误详情；明确索引属于产物数组 | 第一次索引越界后新增研究并反复读取材料 | 归档参数错误可在一次明确修正内解决；仅由索引错误引起的额外联网请求为 0；独立测试集报告首次保存通过率 |
| P0 | 保存前一次性报告可确定的类型覆盖、索引和日期问题；返回 `day`、字段路径、期望范围及实际值 | 本次先修索引，再发现 practical 覆盖缺失 | 同一已知资料集的连续 `needs_revision` 次数下降；分别统计错误码、修正次数、额外 Planner 秒数；不为凑覆盖伪造证据 |
| P0 | 把预算金额、币种、总额/每日口径、涵盖项目显式传入研究和保存校验；对规划说明执行语义一致性检查 | 1500 元两天总预算漂移为每日预算，仍通过现有交付校验 | 此例必须被识别；固定预算回归集的口径错误漏检为 0；真实评测单独记录预算语义正确率，不能用结构通过率替代 |
| P0 | 补齐请求级观测：Planner、研究、工具、数据库保存、首个可用产物和浏览器最终呈现分别计时 | 当前只能用请求账本和数据库时间戳重建，工具状态还混用了技术成功与业务退回 | 每轮可关联 request/generation/turn ID；记录业务结果码；父子请求可去重汇总；同时产出后端总时长与点击到可用结果时长 |
| P1 | 用归档结构失败构建适配器回放集；将明确的格式包裹与缺失字段分开处理 | 第一次研究顶层多字段，且 7 条 finding 缺目的地索引 | 按失败类型报告原始与转换后通过率；只做无歧义转换；不静默补目的地、日期或来源；格式修复新增模型请求数受显式上限约束 |
| P1 | 对本地输入错误使用可解释的修正指导；新增研究必须对应缺失证据，不因索引越界自动换工具 | 第 64–66 次相关请求累计 31.165 秒，最终仍复用第 62 次材料 | 无新增证据需求时额外研究次数为 0；报告每轮重复研究率和重复材料读取率；比较独立案例的完整任务 p50/p95 |
| P1 | 核对 OpenRouter 搜索参数与回执计数，保存实际搜索数和费用，并明确是否有批量计数 | 每次配置 max_uses=2，却报告 6 次搜索 | 请求配置与返回计数可以解释；上限能被实测验证；异常计数进入诊断，不能把未知数默认为 0 |
| P1 | 以相同任务对比 Qwen、GLM及同模型 fallback 开关；只对可恢复的 429 做有界退避或切换 | 组件实验与集成 fallback 配置不同；本轮含 429 | 报告 HTTP 成功率、有效研究交付率、完整攻略成功率、429 恢复率、完整时长及成本；限制重试次数和总时限 |
| P1 | 中间模型回合约束为精简的工具调用；最终答复仅根据已保存产物组织，并在页面呈现最新活动状态 | 本轮主规划请求占 66.55%，包含较长中间正文；用户看到过夹杂内部工作描述的纯文本 | 记录中间输出 token 数、Planner 调用次数、最终答复时长；最终界面无中间工作叙述；状态只显示最新事件且结束后清除 |
| P2 | 在来源与过期规则允许的前提下复用同版本研究，并让已有兼容材料对 Planner 更易发现 | 本轮研究材料已存在，但其后经历额外研究与读取 | 缓存或复用命中率、无效过期命中数、每轮新研究次数；分别测试日期修改、预算修改及城市修改的失效行为 |

优先级判断基于可修复的实际错误和用户可见质量。单纯提高超时上限不会修正索引、预算或搜索上限问题；单纯换更快的研究模型也不会消除 Planner 的重复决策。验收应同时报告耗时与内容质量，尤其不能通过放宽证据校验来换取表面上的“成功”。

## 10. 尚未观测到的时间与证据限制

前端以 2 秒间隔串行轮询临时 turn 状态。轮询与后台工作并行，不是每一步工具都额外暂停 2 秒。健康连接下，后台完成到下次状态发现通常增加至多一个轮询间隔，再加请求和渲染时间；浏览器后台节流、断连及重试会改变这个范围。本次没有保留客户端网络与绘制日志，不能给出实际轮询次数、轮询占比或精确的点击到显示耗时。

当前没有供应商排队、联网搜索、模型生成、传输的独立计时，没有首 token 或流式输出数据，也没有逐条数据库操作耗时。本次调用中 `provider_calls` 表没有相应时间范围的记录，因此不能借该表进一步拆分。文中毫秒级数字反映本地记录的精度，不意味着所有隐含阶段都已具备毫秒级测量能力。

保存错误的两条代码既与原始参数和当时实现吻合，也经真实保存函数的离线内存回放确认；原始工具返回全文没有持久化，回放结果不冒充当时的原始响应日志。已有模型回执仅用于读取结构化动作参数及相关合同形态，不作为事实正确性的独立证据。

本文没有访问引用页面重新核查事实，没有重新测量汇率，没有新增付费请求，没有更改模型、冷却参数、数据库或运行服务。当前建议的收益仍需后续验证。
