# 对话与行程上下文管理

更新：2026-10-26。已实现并完成下述离线及H5验收。对应今日复测R8：旧上海行程调整错误恢复最新西亚对话，草稿未发送；调整弹窗残留。

行程消息保存`context={conversationId,messageId,runId,tripId}`。恢复以只读`GET /api/trips/:tripId/context`为准（兼容直接传来源runId）：检查成功任务、任务内行程ID、任务原会话及原会话中该行程的助手消息锚点，返回`{conversation,context}`。不能用最近会话替代；历史行程从自身任务与原消息恢复，不搜索无关会话、不调用模型。没有原会话的独立规划结果明确失败。

H5与微信共享客户端维护会话代次。重新开始、恢复其他行程立即使旧代次失效并取消其查询、聊天、详情和选票请求；每个请求捕获发起时的会话ID，只接收归属一致的消息。迟到POST会在任务ID到达后取消；迟到进度、结果及行程保存回调不能更新当前会话或storage。切换期间不发业务请求；恢复失败保持阻塞，需重试恢复或明确重新开始，不能退回最新会话或误发成新对话。

行程“继续调整”先关闭抽屉，恢复所属会话成功后才填草稿并打开规划页；切换会话使规划组件清空旧消息并重新读取。离开行程页清理弹窗。恢复只恢复该原对话最新已保存历史，不提供会话列表、跨用户认证或历史消息分支；快捷调整仍只在本次浏览保留，不宣称已实现真实持久改行程。

## 多行程列表

真实展示行程ID为`live-<runId>`，任务文件名为无前缀UUID；两者分别保存为context.tripId/context.runId。列表、详情、归档和会话恢复按这个明确映射读取，不能直接把展示ID当任务文件名。定位真实历史文件时已发现并加入对应回归，避免出现“磁盘有行程、列表却为空”。

调整消息带显式`tripContext={conversationId,messageId,runId,tripId}`，后端在调用模型前核对原会话与助手消息，不能只凭目的地名称猜测调整对象。聊天输入和规划约束携带该已保存行程的ID、日期、日程与航班摘要。H5/微信同时保存会话ID与行程引用；重新开始会清除两者，刷新后仍能定位所选行程。生成新版本后，后续调整引用自动切到新版本所属任务与消息，而不是继续指向此前选中的旧版本。同一原对话的既有历史保持完整，不自动裁剪或分支。规划与审核仍各用该任务独立DSH会话；原账户、模型和角色思考档位不变。

`GET /api/trips`从本机已保存成功任务返回所有真实行程摘要，按完成时间倒序，限制同时读12份文件；列表不加载全套逐日内容，不调用模型。历史成功结果直接纳入，不再只有最近一份。点击后按所选ID读取完整行程并恢复其原对话；没有原对话的独立结果只可查看，不能借用当前会话调整。“新建行程”明确清空当前会话，保留已有行程。

`POST /api/trips/:id/archive {archived:boolean}`仅保存该行程归档标记到`backend/data/trip-library/`，不改原行程和对话；刷新或重启后仍可列出、恢复。列表读取失败显示错误与重试，不回落到固定样例。当前为本机单用户文件存储，不是多账户隔离服务。
